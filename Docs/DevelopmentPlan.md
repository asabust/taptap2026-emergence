## 执行与交接约定

执行者先读完整 GDD，再读本文件及当前项目中的 AGENTS.md／CLAUDE.md（如果存在）。开发任务必须指明阶段，不默认一次完成全部游戏。已确认的玩法以 GDD 为准；本文件提供工程边界，不添加新的玩法。阶段 7、8 的待定产品选择须在开始对应阶段前确认，不影响阶段 1～6。

工作目录为 Unity 项目 `/Users/aoi/UnityProjects/taptap2026-emergence`。Unity 版本为 2022.3.62f3。开始前检查当前文件与改动，保留用户已有代码、Demo、场景和资源，不使用清空目录或重写整个框架的方式接入。

程序集约束：Data 只放数据类型，不依赖 Core 或 Gameplay；Core 只添加可复用的读写等能力；关卡校验、编辑操作和玩法规则属于 Gameplay。已有 DataLoader 专门加载 database.json，不把单关卡读取混入该流程。使用现有 Newtonsoft.Json，不新增序列化依赖。

建议模块目录：`Runtime/Data/Levels`、`Runtime/Core/IO`、`Runtime/Gameplay/Levels`、`Runtime/Gameplay/LevelEditor`，场景统一放 `Assets/Scenes`，之后新增的 Scene 也使用该目录。类名和目录为推荐实施方案，可适当调整，但必须记录最终接口供下一阶段使用。关卡来源使用现有 JSON 示例的 cells 列表，避免另加一份 playerPosition 作为文件中重复真值；运行状态可拆出玩家坐标。

Git 提交约定（用户于 2026-10-17 指定）：每一步执行完成并通过对应验证后，提交一次 Git，说明具体功能与验证结果。美术资源（含对应导入元数据、字体图集及美术场景调整）单独提交，与功能代码／文档分开。仅纳入该步骤相关修改，保留用户其他未提交改动；未要求推送时只做本地提交。

每阶段交付时提供：修改文件、公开接口及依赖、Unity 中如何打开和操作、实际完成的检查、尚未完成的检查，以及下一阶段可直接使用的入口。在 `Docs/ImplementationStatus.md` 记录阶段状态和实际接口；没有执行的 Unity 编译、Play Mode 或浏览器验证，不能报告通过。

场景与资源交付必须可复现：使用可用的 Unity 工具创建并验证 Scene／Prefab；若无法直接操作 Unity，提供放在 `Assets/Game/Editor` 的明确菜单构建工具与操作说明，不凭猜测手写复杂场景 YAML，也不声称场景已验证。生成工具不要自动覆盖已有同名场景，应明确报告冲突。

首版不开发手机版编辑器、无限撤销、编辑器操作撤销、规则插件系统或自动求解器。实现玩法数据与表现分开，使同一逻辑能用于两个场景及无画面的规则测试。

阶段可交给不同执行者，但必须顺序交接依赖：1 → 2 → 3；1 → 4 → 5；3 与 5 都完成后才能做 6。阶段 2 完成基础拾取与画笔，阶段 3 连接目标面板；阶段 4 完成规则与操作接口，阶段 5 连接具体 HUD，避免重复开发。

## 1. 关卡数据与读写

- Data 定义关卡、地形、初始细胞、玩家位置、两个死亡规则开关、分身上限、迭代上限与三类目标结构。
- Gameplay 定义运行状态及分身来源标记，与关卡初始数据分开。
- 实现 JSON 读写、默认值与校验；默认保存到 `Assets/StreamingAssets/Levels`，关卡 ID 对应文件名。
- 支持保存不完整草稿；试玩前要求恰好一个玩家、至少一个完整目标及合法坐标。未知版本或规则报告错误。

交付验收：保存后重新加载的数据一致；缺省分身额度为 0、迭代上限为 1,000；错误数据不进入试玩。

实施合同：提供 `Serialize/Deserialize`、`Load/Save`、`ValidateForPlay` 与关卡深拷贝入口（名称可调整）。缺失字段与非法值区分：缺失上限使用默认值，负分身值、非正迭代上限、尺寸越界报告错误。未知 schemaVersion 不继续解释。保存前先序列化到临时文件，再替换目标文件，写失败不损坏已有文件。关卡 ID 不允许路径分隔符，避免文件名逃出保存目录。

校验至少覆盖：重复地形坐标、重复细胞坐标、非 floor 上的细胞、玩家数非 1、空目标列表、空多位置列表、重复目标坐标、目标不在 floor 上、未知条件类型与比较符。JSON 解析失败不得把当前草稿清空。初始满足目标是提示而非数据错误。提交一份小型合法示例及针对解析／回读、默认值、非法坐标的验证；此阶段不制作 UI。

## 2. 棋盘显示与基础编辑

- 创建 LevelEditor Scene，先使用可辨识的临时素材显示地形、普通细胞、玩家和目标。
- 实现 1～30 的 x/y 尺寸、逻辑坐标与点击拾取。
- 实现单格画笔及删除、唯一玩家放置、目标格编辑。
- 实现居中扩缩、统一坐标偏移及超出范围内容丢弃。

交付验收：不规则外轮廓与内部空洞可编辑；奇偶尺寸变化、玩家及目标被裁切的行为符合 GDD。

实施合同：编辑会话持有唯一草稿，画面由草稿刷新；点击位置转成整数坐标，UI 上的点击不落到棋盘。画笔先提供 floor、wall、普通细胞、玩家与分层删除；目标点击入口暴露给阶段 3。放置玩家时移动已有玩家；放置普通细胞到玩家格时拒绝，避免静默删除玩家。对象画笔不能在非 floor 格生效。临时配色与标记要区分空地、墙、普通细胞、玩家和目标。

尺寸测试必须包含 5→6、6→5、6→4，以及同时改变 x/y；使用 GDD 的 floor 偏移公式，负数不能用向零截断。未变化的内容、目标和玩家必须使用相同偏移。新建时清除上一草稿对象；拖动连续绘制不是本阶段要求。

## 3. 编辑器配置与文件操作

- 设置两个死亡开关、分身存活上限、迭代上限。
- 添加角色位置、细胞数量、细胞多位置覆盖目标，全部同时满足。
- 接入新建、加载、保存和另存为；显示草稿校验与初始满足目标提示。

交付验收：能独立制作、保存、重开一张完整关卡；两个死亡规则同时关闭时允许使用并显示提示。

实施合同：实现尺寸输入、两个规则勾选框、两个上限输入、目标类型列表及参数面板。位置目标编辑通过棋盘拾取；多位置支持添加／删除，显示格子坐标。仅支持严格 `>`／`<`，不自行增加等于条件。未填分身值为 0、未填迭代值为 1,000；非法输入显示字段错误，不静默改成合法值。

文件 UI 显示当前关卡 ID 与保存结果。加载失败保留草稿；另存为新 ID，覆盖同 ID 的文件。以固定默认目录完成首版，不需要原生文件对话框。验收需通过 UI 制作一关并重开，不能仅依赖阶段 1 的序列化测试。

## 4. 共用玩法逻辑

- 实现四向单次移动、地形与存活细胞阻挡。
- 基于上一轮完整状态同步执行死亡规则，不自动繁殖；玩家参与八邻域计算但不死亡。
- 实现分身放置状态、八邻格合法性、同时存活上限、全棋盘回收及名额释放。
- 实现统一目标检查与轮数限制；最后一轮后允许继续操作，超限迭代不改变棋盘并提示失败。

交付验收：用小棋盘验证孤独、拥挤、规则关闭、玩家干预、分身死亡释放名额；组合目标不累计历史达成状态。核心规则用少量有明确预期结果的测试验证。

实施合同：提供可复用会话入口，如 `TryMove`、`TryCreateClone`、`TryRecycleClone`、`TryIterate`，返回成功／拒绝及原因；逻辑不直接打开面板。维护 Playing／Won／Failed 状态，胜利或失败后阻止棋盘普通操作，阶段 5 的撤销／重置可以恢复会话。无效操作不修改布局、额度或轮数。同步迭代先读全量旧状态再应用结果，不能边遍历边删除。

分身创建使用八邻格，移动只使用四邻格；回收全棋盘但仅限分身。覆盖与数量目标均包含分身，不包含玩家。所有有效变化后评估当前全部目标，无目标列表不能按空集合默认为胜利。达到上限时仍 Playing；再次尝试迭代才 Failed，且状态数据与历史不推进。

必要例子：一个邻居的普通细胞在玩家补足第二个邻居后存活；已有三个邻居的细胞在玩家补成四个后死亡；关闭对应规则则保留；空格有三个邻居仍为空；满额创建被拒绝；回收普通细胞被拒绝；数量严格等于阈值不满足；两种目标先后成立但不同时成立时不胜利。

## 5. 撤销、重置与试玩 HUD

- 每次迭代前深拷贝棋盘、来源标记、玩家位置与轮数，保留最近 100 份快照。
- Z 按迭代恢复，丢弃该迭代后的移动、分身和回收；无历史时不改变状态。
- R 恢复初始关卡并清空历史、失败状态；名额从存活分身数恢复。
- 显示目标、轮数、分身数与操作按钮；统一处理放置、回收、结算中的输入。

交付验收：多轮恢复准确；第 0 轮、历史超过 100 轮、超限失败后回退、恢复分身来源均正确。

实施合同：统一协调有效迭代与历史写入，仅成功迭代保留其前快照；超限尝试、非法动作和单纯移动不记录。使用可淘汰最早项的有界历史，避免无界增长。快照不共享数组、列表或可变细胞对象；关卡初始副本也必须独立。

输入接入 Input System：方向键、空格、Z、R 及按钮走同一操作入口。分身模式只允许选择合法格与取消；回收模式高亮分身、可取消，操作一次后返回移动。对同时输入采用确定的处理顺序并记录，单帧不执行多个状态动作。HUD 在失败时提供 Z／重试入口，无历史时撤销按钮禁用；恢复状态后关闭失败提示。分身额度为 0、满额、无合法邻格或无分身可回收时给出清晰反馈。

历史例子：分身 A → 迭代 → 回收 A、分身 B、移动 → Z，应恢复迭代前 A 与玩家位置，B 不存在；存活分身数准确。另以不易初始通关的测试关验证 101 次迭代只保留 100 份记录。

## 6. 编辑器内试玩与首个可玩关卡

- 编辑模式校验并复制草稿，切到试玩模式，锁定编辑画笔。
- 结束试玩丢弃运行状态，恢复草稿与编辑视图；胜利／失败提供重试与返回编辑。
- Gameplay Scene 使用相同棋盘与规则组件，验证两个场景结果一致。
- 制作至少一张需要站位、分身和迭代的小关卡，记录一条可通关操作序列，检验操作是否形成有意义的选择。

交付验收：无需保存即可试玩；R 使用试玩初始副本；结束试玩不污染草稿、不解锁正式关卡。完成本阶段后再评估正式内容规模。

实施合同：编辑会话、试玩初始副本、当前运行状态三者独立；进入试玩先校验，失败则继续编辑并展示原因。退出试玩清理输入订阅、运行对象与历史，恢复草稿和原编辑视图，不重新从磁盘加载。重复进出试玩不能累积 UI、对象或输入回调。Gameplay 和编辑器试玩只使用同一个规则会话实现。

提交测试关卡 JSON 与可复现的操作序列，列明每次迭代后轮数、分身数、关键格存活状态和最终目标；不能只凭“看起来可通关”验收。正式关卡不在此阶段批量制作。

## 7. 正式标题、选关与结算

开始前定案：局部放大图的进入方式、结算表现、顺序解锁、进度保存范围、暂停与失败面板按钮。

- 创建标题与人体选关流程，关卡展示配置按 ID 关联棋盘 JSON。
- 实现人体按钮、局部彩色放大图、描述、进入关卡和返回。
- 接入 Gameplay、完成状态、关卡解锁与结算；处理末关与重复通关。
- 保存正式进度；编辑器试玩不写入正式存档。

交付验收：标题到游玩再到下一关的完整路径可用；退出重开能恢复进度。

## 8. 叙事、美术与发布验证

- 定义对话表现与触发点，再接入文本及已读行为。
- 替换美术和音效，检查不同窗口尺寸下棋盘、文字及 HUD 的可读性。
- PC 与桌面 WebGL 分别验证关卡读取、进度保存、输入及完整流程；WebGL 不能直接沿用桌面文件路径访问方式。
- Android 留作后续独立工作：横屏、手势仲裁、缩放平移、安全区域与真机验证。

每个阶段完成对应验收后继续；若原型暴露玩法问题，先更新 GDD 和受影响步骤，不提前堆叠正式关卡或终局内容。
